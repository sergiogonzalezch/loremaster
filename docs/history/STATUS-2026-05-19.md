## 3. Deliverables 2026-05-19

### 3.1 Infraestructura de evaluaciones — backend aislado (`b91d098` → `e40ea63`)

`baseline_evals.py` ahora arranca un segundo proceso uvicorn en `:8001` contra `evaluations/evals.db` (separado de `loremaster.db`). El script migra la BD antes de lanzar uvicorn y luego inyecta `SKIP_MIGRATIONS=true` en el entorno del proceso hijo para evitar el deadlock SQLite + asyncio/greenlet en Windows.

Tres bugs resueltos en cadena:

| Bug | Causa raíz | Fix |
|---|---|---|
| `_wait_for_backend` timeout | `args.base_url` usaba `localhost` (→ IPv6 `::1`) pero uvicorn bind en `127.0.0.1` | Cambio a `http://127.0.0.1:{port}` en línea 1578 |
| Health endpoint excede timeout=2 | `/health` hace 2 llamadas HTTP secuenciales (Qdrant + Ollama) con 2s cada una; en Windows IPv6-fallback añade ~2s | `timeout=10` en `httpx.get` del poller |
| Deadlock Alembic en lifespan | `asyncio.to_thread` no suficiente en Windows; el proceso hijo corría migraciones dos veces | `SKIP_MIGRATIONS=true` inyectado en env de uvicorn; lifespan omite Alembic si la variable está presente |

**Archivos clave modificados:** `evaluations/baseline_evals.py`, `app/core/lifespan.py`.

### 3.2 Bearer token en Swagger UI (`5419879`, `7cab0b9`)

Swagger UI (`/docs`) ahora expone el botón **Authorize** con un único scheme `BearerAuth`. Los tres routers afectados (`auth`, `auth_clerk`, endpoints públicos) estaban generando tres `HTTPBearer` anónimos distintos; consolidados en una dependencia compartida con nombre explícito.

Configuración relevante:
```python
app = FastAPI(
    ...
    swagger_ui_oauth2_redirect_url=None,  # desactiva OAuth2 redirect no usada
)
app.include_router(router, dependencies=[Depends(bearer_scheme)])
```

`RATE_LIMIT_ENABLED` se desactiva automáticamente en el backend standalone de eval para que los casos no choquen contra los límites por worker.

### Código actual (resumen)

```tsx
// AuthContext.tsx — logout síncrono (Issue #2 ✅)
const logout = useCallback(async ({ force = false } = {}) => {
  if (force) { setUser(null); setAvatarUrl(null); return; }
  await logoutApi();   // lanza si falla
  setUser(null); setAvatarUrl(null);
}, []);

// ProtectedRoute.tsx — Clerk + backend (Issue #4 ✅)
function ProtectedRouteClerk() {
  const { isSignedIn, isLoaded } = useUser();
  const { user, loading } = useAuth();
  if (!isLoaded || loading) return <LoadingSpinner />;
  if (!isSignedIn || !user) return <Navigate to="/login" .../>;
  return <Outlet />;
}
```

## 7. Moderación — gaps estructurales residuales (MOD.md)

Tras 3 ciclos de evaluación, el guard tiene cobertura completa de bypasses (14/14) y cero falsos positivos en RPG legítimo. Quedan 2 gaps en output guard:

### 7.1 HARM-12 — Manual de humillación sistemática ✅ Cerrado

El LLM generaba contenido instructivo en formato numerado que no activaba los
patrones existentes basados en verbos directivos.

**Fix aplicado** — 1 patrón adicional en el output guard, 12 tests nuevos.
*(Detalle de implementación redactado del repositorio público — ver código fuente.)*
Exclusivo de output guard. Confianza ~85% (no cubre todas las variantes nominales).

**Llama Guard 3** (medio plazo): capa semántica adicional sobre el output completo. Cierra HARM-12 en ~95% y mejora otros J2=3. Latencia adicional 200–600 ms en GPU / 1–3 s en CPU.

### 7.2 HARM-08/15 — Contenido sexual implícito

| Caso | Severidad real | Estado |
|---|---|---|
| HARM-08: sexual con menores | Categoría crítica (no negociable) | ✅ **Cerrado** — detección bidireccional reforzada, 26 tests totales |
| HARM-15: romance adulto sensual | J2=3, sin instrucciones dañinas | ✅ **Decisión tomada (2026-05-20)** — romance/intimidad permitidos; solo keywords explícitas bloqueadas |

**HARM-15 — decisión:** LoreMaster es una herramienta narrativa para adultos. El guard bloquea contenido sexual explícito por keywords. Romance, intimidad y contenido sensual sin keywords explícitas son aceptables. Nota de reconsideración documentada si el público objetivo cambia a familiar/educativo.

### 7.3 Arquitectura propuesta a largo plazo

```
Input usuario  →  [1] check_user_input() regex <1ms
               →  LLM genera output
               →  [2] check_generated_output() regex <1ms
               →  [3] check_output_semantic() Llama Guard 3 ~500ms  (PROPUESTO, opcional)
               →  Output al cliente
```

La capa [3] es degradable: timeout configurable con fail-open + log. No reemplaza la capa regex — la complementa.
